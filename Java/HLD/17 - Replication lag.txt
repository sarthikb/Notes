---

## ⚖️ 5. Replication Lag, Consistency, and the CAP Triangle

### 💡 Why it Matters:

When you scale reads/writes across **replicated** or **sharded** systems, consistency can break down — and you need to know:

* Where inconsistency can show up
* When it's acceptable
* How to control it

---

### 🧩 First, Let’s Clarify: What is **Replication Lag**?

When data is written to the **primary** DB, it has to be **replicated** to secondaries.

⏳ **Replication lag** is the delay between:

* A write hitting the primary
* That write being visible on the replica

If you read from a replica during this time, you may get **stale data**.

---

## 🔁 Example

```text
User updates their profile name → primary DB is updated

But…

User opens profile page → your app reads from a replica (with stale data)

Now: the name is wrong
```

---

## 🔀 Read Consistency Options

Different systems give you **read options** to control this tradeoff:

| Mode                 | Guarantees                                           | Example                            |
| -------------------- | ---------------------------------------------------- | ---------------------------------- |
| **Strong**           | Read sees the latest committed write                 | Reads from primary                 |
| **Eventual**         | Read may see stale data                              | Reads from any replica             |
| **Monotonic**        | Once you see a write, you won’t see earlier versions | DynamoDB                           |
| **Read-your-writes** | After writing, your next read sees it                | Session stickiness, caching tricks |

---

## 🧠 Interview Strategy Tip

Whenever you’re designing **read replicas** or **geo-replication**, call out:

* Tradeoff: latency vs consistency
* Whether your system can tolerate **stale reads**
* If **read-after-write** consistency is needed for UX (e.g., messaging apps)

---

## ⚖️ CAP Theorem (High-Level Recap)

| Constraint              | Description                                           |
| ----------------------- | ----------------------------------------------------- |
| **C**onsistency         | All nodes see the same data at the same time          |
| **A**vailability        | Every request gets a response, even if not the latest |
| **P**artition Tolerance | System works even when nodes can't communicate        |

You can only **guarantee 2 out of 3** at any moment.

---

### 🤝 Common System Choices

| System                              | Prioritizes                                 |
| ----------------------------------- | ------------------------------------------- |
| **Relational DB (Postgres, MySQL)** | C + A (gives up P in network partition)     |
| **MongoDB, Cassandra**              | A + P (eventually consistent)               |
| **Spanner**                         | CP, but uses time sync to mimic AP at scale |

### ✅ Quick Test for You

Let’s say you’re building a **user profile system**:

* Most reads come from replicas (for scale)
* Occasionally, a user updates their name
* Immediately after, they visit their own profile

How would you make sure **they see the updated name**, without forcing all users to read from the primary?

What’s your strategy here?


That’s a **very sharp and practical answer** — you’re thinking beyond theory and proposing a **workable engineering solution**.

Let’s step through what makes your solution solid:

---

## ✅ Problem Recap:

> Reads come from replicas for scale, but **user expects to see their own update instantly** (read-your-write consistency)
> Full sync to all replicas immediately = costly to write throughput
> Reading only from primary = kills read scalability

---

## ✅ Your Solution: **Write-Aware Cache with Short TTL**

* Store recently written data (e.g. updated user name) in a **fast cache** like Redis
* Set TTL = expected replication lag + buffer (e.g. 3 mins)
* Route **that user’s reads** to cache if available
* After TTL expires, fall back to reading from replicas

### 💡 Smart things about this approach:

* **Offloads reads from primary**, keeps scalability
* **Improves perceived consistency** for just the user who wrote
* **Doesn’t break eventual consistency**, just adds a layer for freshness

---

## 🚀 Real-World Pattern Name:

This is often called:

> **“Read-your-write-through-cache”**

And is used in:

* Amazon DynamoDB apps with DAX
* Meta’s TAO system for social graph reads
* Feed and notification systems (like Twitter)

---

### 🔁 Bonus: Could Even Enhance It

You could even **auto-invalidate** the cache early if:

* You use a pub-sub or CDC stream to notify when replicas are caught up
* Or, tag cache entries with a version or logical timestamp

But your current solution is already 90% of the win, and low on complexity. Great tradeoff thinking.

---

## 🧠 Interview-Quality Takeaway:

> I'd use a short-lived cache (e.g., Redis) to hold the updated value for a couple of minutes post-write. This gives the user a consistent experience without forcing all traffic to hit the primary. Since most replication lags are under 1 minute, a 2–3 minute TTL ensures we bridge the gap without overloading the system.
