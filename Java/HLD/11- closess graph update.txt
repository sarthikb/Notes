Let’s break it down into a **production-grade architecture** for maintaining closeness scores, including:

---

## 🎯 Goal: Dynamically Update Closeness Scores Based on User Activity

Each user-to-user relationship has a **closeness score**, which:

* ⬆️ Increases on interaction
* ⬇️ Decays over time if no interaction

This enables:

* Better feed ranking
* Smarter story ordering
* More accurate suggestions (e.g. tag suggestions, chat prioritization)

---

## 🧱 Components for Dynamic Closeness Scoring

| Component                     | Responsibility                                                |
| ----------------------------- | ------------------------------------------------------------- |
| `InteractionEventBus` (Kafka) | Streams activity events like `liked`, `messaged`, `searched`  |
| `ClosenessScoreService`       | Consumes activity events and updates edge weights in graph DB |
| `GraphDB` (Neo4j, TigerGraph) | Stores (userA)-\[:FOLLOWS {score: 0.87}]->(userB)             |
| `ScoreDecayScheduler`         | Periodic job to reduce scores for stale connections           |

---

## 📈 Scoring Model: Event-Based Weighting

Each interaction type has a custom weight:

```yaml
Interactions:
  like: +0.1
  comment: +0.2
  message: +0.3
  profile_view: +0.15
  search: +0.05
  story_reply: +0.25
```

> **Example**: If user A comments on B’s post and then views their profile:

* Score(A→B) = previous\_score + 0.2 + 0.15

You can tune the weights via experimentation or learning from usage data.

---

## ⏳ Decay Model

We don’t want the score to stay high forever. So, we introduce:

### 🔁 Periodic Decay Job

* Triggered by `ScoreDecayScheduler` (runs daily)
* Scans edges in graph
* Applies:

```python
new_score = current_score * decay_factor
```

e.g., decay factor = 0.95

🧠 You can make this smarter:

* Decay **faster** if no activity for 30+ days
* Or decay **per interaction type** (e.g., messages decay slower than likes)

---

## 🧠 Why Do This?

It reflects **real-world social drift**:

* You might’ve interacted a lot with someone last year…
* But if you haven’t talked lately → feed should de-prioritize their posts

It keeps:

* Feeds more relevant
* Notifications and suggestions smarter
* ML models leaner (you filter out old/unimportant relationships)

---

## 🚀 Optimization Tip

If you're scaling this to millions of users:

* Use **batched updates** to the GraphDB (not one write per event)
* Partition the graph data by user\_id for horizontal scaling
* Use **Bloom filters** or in-memory cache to skip updates for inactive edges

## 🧠 How Instagram *Actually* Handles Closeness & Feed Ranking (based on published talks, papers, and industry patterns)

Instagram doesn’t publicly share all internal details, but based on what’s known and extrapolated from Facebook architecture (Meta shares infra between products), here’s how it works **in practice**:

---

### 🏗️ 1. Does Instagram Use a Graph DB?

> **No, not a traditional graph DB like Neo4j in hot path.**

Instead, Meta/Instagram use **custom graph storage systems** like:

* **TAO** (for Facebook) — a **caching graph API layer** on top of sharded MySQL
* Internally optimized **Graph Indexes** on top of RocksDB or other key-value stores

These are:

* **Highly available**
* Horizontally scalable
* Sharded by user ID

So closeness data **isn’t just stored in a graph DB**, but exposed via **custom APIs/services** optimized for read latency.

---

### 🔄 2. How is Closeness Score Updated?

Closeness scores are typically:

* **Precomputed**
* Stored in a **ranking signal store** per user
* Updated **asynchronously** by a dedicated **“Signals” pipeline**

✅ **Yes**, there's a **Closeness Signal Service** (or similar), which:

* Consumes user interaction events (from Kafka)
* Maintains closeness vectors per user
* Writes them to a **keyed, fast-access store** (e.g. RocksDB, HBase, or custom KV store)

It may look like:

```
closeness:user123 = {
  userA: 0.81,
  userB: 0.42,
  ...
}
```

---

### 🧩 3. Who Reads It? Does Ranker Call It?

YES — the **Ranking Service**, used during feed generation, **calls this Closeness API** (or reads from a cache of it) when computing score per post.

So:

```plaintext
[FeedService] → Gets list of post IDs
             → For each post, calls:
               - ClosenessService (user → author closeness)
               - Engagement score
               - Post freshness
             → Computes ranking score
             → Returns top N
```

OR — in high-performance settings, **this is precomputed** too.

---

### ⚙️ 4. Why Not Have Multiple Services Access Graph DB?

Because of your exact concern: **violates service boundaries**, **adds complexity**, **kills performance**.

So instead:

✅ The **Closeness Score Service** exposes an **API or gRPC interface**, e.g.:

```http
GET /closeness?from=user123&to=user456
→ 0.87
```

OR bulk:

```json
POST /bulk_closeness
{
  "from": "user123",
  "to": ["user456", "user789", ...]
}
```

And it returns a map of closeness scores.

---

### 🧠 In Summary:

| Problem                       | How Instagram solves it (or similar large-scale apps)     |
| ----------------------------- | --------------------------------------------------------- |
| Graph DB performance          | Don't use raw graph DBs — use optimized key-value storage |
| Access from multiple services | Expose API from **Closeness/Signal Service**              |
| Signal computation            | Done via Kafka + background jobs                          |
| Feed ranking latency          | Either precomputed, or use fast cached signal lookups     |
| Score decay                   | Periodic jobs run in Signals Service, decaying weights    |

---

## 🔚 Closing Thought

> “Graph DB” in this context is more of a **data model** than a **technology**.
> What matters is how you structure and serve the **graph-based ranking signals** — not whether you use Neo4j or a service exposing fast vectors.
