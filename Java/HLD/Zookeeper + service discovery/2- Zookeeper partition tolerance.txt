## 1️⃣ How READ and WRITE work with Leader & Followers in ZooKeeper

ZooKeeper uses a protocol called **ZAB (ZooKeeper Atomic Broadcast)**.

### ZooKeeper cluster example

```
ZK1 – Leader
ZK2 – Follower
ZK3 – Follower
```

(3-node ensemble → quorum = 2)

---

## 🔹 WRITE PATH (Strong Consistency)

### Key rule

> **All writes go through the leader**

### Step-by-step write flow

1. **Client sends a write request**

   * Client can connect to **any** ZooKeeper server (leader or follower)

2. **If connected to follower**

   * Follower **forwards the write** to the leader

3. **Leader proposes the write**

   * Leader assigns a **zxid** (monotonically increasing transaction id)
   * Leader broadcasts proposal to all followers

4. **Followers ACK**

   * Followers write proposal to disk
   * Send ACK to leader

5. **Quorum ACK**

   * Once leader receives ACK from **majority (quorum)**

6. **Commit**

   * Leader sends COMMIT message
   * Followers apply change to memory
   * Client gets success response

### ✔ Result

* All nodes apply writes **in the same order**
* Strong consistency guaranteed

---

## 🔹 READ PATH (Fast Reads)

ZooKeeper allows **local reads**.

### Step-by-step read flow

1. Client sends read request
2. Server (leader or follower) serves read **from local memory**
3. No coordination needed

### ❗ Why this is safe?

Because:

* Writes are globally ordered
* Followers never apply uncommitted writes
* So local reads are consistent

---

## 2️⃣ Is ZooKeeper CP? What does that mean?

Yes — ZooKeeper is a **CP system** in the CAP theorem.

### CP means:

* **Consistency**: All clients see the same data
* **Partition tolerance**: Network partitions can happen
* **Availability** is sacrificed when consistency cannot be guaranteed

---

## 3️⃣ What happens during a network partition?

### Case A: Partition WITH quorum

Example:

```
Partition 1: ZK1 + ZK2   (2 nodes)
Partition 2: ZK3         (1 node)
```

✔ Partition 1 has quorum → **cluster continues**

* Leader exists
* Reads & writes work

❌ Partition 2 has no quorum

* ZK3 becomes **read-only**
* No writes allowed

---

### Case B: Partition WITHOUT quorum

Example:

```
Partition 1: ZK1         (1 node)
Partition 2: ZK2 + ZK3   (2 nodes)
```

✔ ZK2/ZK3 form quorum

* New leader elected
* Cluster continues

❌ ZK1 isolated → read-only

---

### Case C: No partition has quorum (rare but important)

Example:

```
ZK1 | ZK2 | ZK3   (all isolated)
```

❌ No quorum anywhere
❌ **ZooKeeper becomes unavailable**

* No writes
* Reads often disabled or stale

This is **by design**.

---

## 4️⃣ Does this mean ZooKeeper has a Single Point of Failure?

### ❌ NO — ZooKeeper does NOT have a single point of failure

Here’s why:

| Concern          | Reality                        |
| ---------------- | ------------------------------ |
| Leader failure   | New leader elected             |
| Follower failure | Cluster still works            |
| Node crash       | Tolerated                      |
| Partition        | Works as long as quorum exists |

### ✔ Failure tolerance

* 3-node cluster tolerates 1 failure
* 5-node cluster tolerates 2 failures

---

## 5️⃣ Then why does availability go down?

This is the **CAP tradeoff**.

ZooKeeper chooses:

```
Consistency + Partition tolerance
```

and sacrifices:

```
Availability (temporarily)
```

### Why is this necessary?

Imagine two partitions both accepting writes:

* Data divergence
* Broken invariants
* Corrupt coordination state

ZooKeeper refuses writes rather than returning incorrect data.

---

## 6️⃣ Why is this OK in real systems?

ZooKeeper is used for:

* Service discovery
* Leader election
* Configuration
* Distributed locks

These require:

* Correctness > availability
* Small data
* Short unavailability acceptable

You don’t store business data in ZooKeeper.

---

## 7️⃣ Summary (Very Important)

### ✔ Reads

* Served locally by leader or follower
* Fast and consistent

### ✔ Writes

* Always go through leader
* Require quorum ACK
* Strong ordering guaranteed

### ✔ Network partitions

* If quorum exists → cluster works
* If no quorum → cluster unavailable (by design)

### ✔ No single point of failure

* Leader is replaceable
* Failure tolerance comes from quorum

---

## 8️⃣ Mental Model (One-liner)

> **ZooKeeper prefers being unavailable over being wrong.**

That’s the essence of CP systems.
