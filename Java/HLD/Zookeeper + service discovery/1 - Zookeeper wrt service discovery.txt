# ⭐ What is Service Discovery?

Service discovery answers one basic question:

> **“Which instances of service X are alive right now, and how do I reach them?”**

ZooKeeper provides this using:

* **strong consistency**
* **ephemeral nodes**
* **watch notifications**

---

# ⭐ Why ZooKeeper is used for Service Discovery

ZooKeeper is good for discovery because it provides:

| Feature                | Why it matters                        |
| ---------------------- | ------------------------------------- |
| Strong consistency     | All clients see the same service list |
| Ephemeral nodes        | Auto-remove dead services             |
| Watches                | Real-time change notifications        |
| Hierarchical namespace | Natural service registry              |

---

# ⭐ ZooKeeper Data Model (Important)

ZooKeeper stores data as a **hierarchical tree of znodes**, like a filesystem:

```
/
 └── services
      └── order-service
           ├── instance-1
           ├── instance-2
      └── payment-service
           ├── instance-1
```

Each znode can store:

* small metadata (IP, port, version)
* type: **persistent** or **ephemeral**

---

# ⭐ Core Idea (High Level)

### ✔ Service instances **register themselves** in ZooKeeper

### ✔ Clients **query ZooKeeper** to find service instances

### ✔ ZooKeeper **automatically removes** dead instances

### ✔ Clients get **notified of changes** via watches

---

# ⭐ Step-by-Step: How Service Discovery Works

---

## 🔹 Step 1 — ZooKeeper Cluster

ZooKeeper runs as a **replicated CP system** (usually 3 or 5 nodes):

```
ZK1 (leader)
ZK2 (follower)
ZK3 (follower)
```

All reads/writes go through quorum.

---

## 🔹 Step 2 — Service Registers Itself

When a service instance starts (e.g., Order Service):

1. It connects to ZooKeeper
2. It creates an **ephemeral znode**

Example:

```
/services/order-service/instance-0001
```

Stored data:

```
{
  "ip": "10.1.2.15",
  "port": 8080,
  "version": "v1"
}
```

📌 **Ephemeral means**:

* Node exists **only while service session is alive**
* If service crashes → znode disappears automatically

---

## 🔹 Step 3 — Client Discovers Service

Client wants to call `order-service`:

1. Client queries ZooKeeper:

   ```
   getChildren("/services/order-service")
   ```
2. ZooKeeper returns:

   ```
   [instance-0001, instance-0002]
   ```
3. Client fetches instance data (IP + port)
4. Client picks one instance (round-robin, random, etc.)

📌 ZooKeeper does **not load balance** — clients do.

---

## 🔹 Step 4 — Watches for Changes (Critical)

Client sets a **watch** on:

```
/services/order-service
```

When:

* a new instance joins
* an instance dies

ZooKeeper sends a **notification** to the client.

Client refreshes the service list.

---

## 🔹 Step 5 — Failure Handling (Automatic)

### Case: Service instance crashes

1. ZooKeeper session expires
2. Ephemeral znode is deleted automatically
3. ZooKeeper notifies all clients watching that path
4. Clients remove the dead instance from their list

🚫 No manual cleanup required.

---

# ⭐ Sequence Diagram (Textual)

```
Service instance ---> ZooKeeper: create ephemeral znode
Client -----------> ZooKeeper: getChildren + watch
ZooKeeper --------> Client: service list
Service crashes
ZooKeeper --------> Client: watch notification
Client ------------> updates local cache
```

---

# ⭐ Why Ephemeral Nodes Are the Key

| Problem           | ZooKeeper solution               |
| ----------------- | -------------------------------- |
| Service crashes   | Ephemeral znode disappears       |
| Network partition | Session timeout triggers cleanup |
| Stale registry    | Impossible (strong consistency)  |

# ⭐ Example Walkthrough

### Services running:

```
order-service:
  instance-1 → 10.0.0.1:8080
  instance-2 → 10.0.0.2:8080
```

Client cache:

```
[10.0.0.1, 10.0.0.2]
```

### instance-2 crashes:

* ZooKeeper deletes `/instance-2`
* Client gets watch event
* Client cache updates to:

```
[10.0.0.1]
```

# ⭐ Common Patterns

### ✔ Client-side load balancing

ZooKeeper gives the list; client chooses instance.

### ✔ Hierarchical services

```
/services/{service}/{instance}
```

### ✔ Version-aware discovery

```
/services/order-service/v1/instance-1
```

---

# ⭐ Summary (Very Important)

* ZooKeeper **does not route traffic**
* ZooKeeper **does not load balance**
* ZooKeeper **only stores service metadata**
* **Ephemeral nodes + watches = discovery**
* Clients maintain a **local cache** of instances
* Strong consistency ensures no stale data
