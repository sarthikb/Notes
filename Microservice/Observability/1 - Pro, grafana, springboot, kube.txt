Below is an **end-to-end, real-world explanation** of how **observability works for multiple Spring Boot services deployed on Kubernetes**, using **Prometheus and Grafana**. I’ll walk through it step by step, from code → Kubernetes → metrics → dashboards → real-time troubleshooting.

---

## Big Picture (What’s happening overall)

You have:

* Multiple **Spring Boot microservices**
* Deployed as **containers** on **Kubernetes**
* **Prometheus** collects metrics from them
* **Grafana** visualizes those metrics in real time

Observability answers **three questions**:

1. **Is the system healthy?** (metrics)
2. **What is it doing right now?** (dashboards)
3. **Why is something slow or broken?** (correlating metrics & alerts)

---

## Real-World Example Scenario

Imagine an **E-commerce platform** with these services:

* `order-service` – handles orders
* `payment-service` – processes payments
* `inventory-service` – checks stock

Each is a **Spring Boot app**, deployed on Kubernetes.

Traffic comes from users → API Gateway → these services.

---

# STEP 1: Instrument Spring Boot for Observability

### 1.1 Add dependencies

Each Spring Boot service includes:

```xml
<!-- Actuator -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

<!-- Micrometer Prometheus registry -->
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

---

### 1.2 Expose metrics endpoint

In `application.yml`:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  metrics:
    tags:
      application: order-service
```

Now each service exposes metrics at:

```
/actuator/prometheus
```

---

### 1.3 What metrics are exposed?

Out of the box, you get:

* HTTP request count
* Request latency
* JVM memory & GC
* CPU usage
* Thread counts
* Error rates

Example metric:

```
http_server_requests_seconds_count
```

---

# STEP 2: Containerize and Deploy to Kubernetes

Each service is packaged as a Docker image.

### 2.1 Kubernetes Deployment (example)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: order-service
        image: myrepo/order-service:1.0
        ports:
        - containerPort: 8080
```

Kubernetes now:

* Runs **multiple replicas**
* Can scale automatically
* Restarts unhealthy pods

---

# STEP 3: Expose Metrics to Prometheus

### 3.1 Kubernetes Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: order-service
  labels:
    app: order-service
spec:
  selector:
    app: order-service
  ports:
    - port: 8080
      targetPort: 8080
```

---

### 3.2 Add Prometheus annotations

```yaml
metadata:
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/path: "/actuator/prometheus"
    prometheus.io/port: "8080"
```

This tells Prometheus:

> “Scrape metrics from here”

---

# STEP 4: Deploy Prometheus on Kubernetes

Usually done using **Helm**.

Prometheus components:

* **Prometheus Server** – scrapes metrics
* **Alertmanager** – sends alerts
* **Node Exporter** – node-level metrics
* **kube-state-metrics** – cluster state

Prometheus periodically:

* Discovers services via Kubernetes API
* Scrapes `/actuator/prometheus`
* Stores metrics as time-series data

---

### 4.1 What Prometheus Sees

For `order-service`, Prometheus now stores:

| Metric       | Example     |
| ------------ | ----------- |
| Request rate | 200 req/s   |
| Error rate   | 2%          |
| Latency      | p95 = 450ms |
| JVM heap     | 70% used    |
| Pod CPU      | 0.6 cores   |

---

# STEP 5: Grafana for Visualization

Grafana connects to Prometheus as a **data source**.

### 5.1 Add Prometheus to Grafana

* URL: `http://prometheus-server`
* Data source type: Prometheus

---

### 5.2 Create Dashboards (Real-World)

Typical dashboards:

#### Service Overview

* Requests per second
* Error rate (4xx / 5xx)
* Latency (p50, p95, p99)

#### JVM Dashboard

* Heap usage
* GC pauses
* Thread counts

#### Kubernetes Dashboard

* Pod restarts
* CPU / memory per pod
* Replica count

---

### Example Grafana Query

```promql
rate(http_server_requests_seconds_count{application="order-service"}[1m])
```

Shows **real-time request rate**.

# STEP 6: Real-Time Deployment & Scaling Scenario

### Scenario: Flash Sale Starts 🚀

1. Traffic spikes from **100 → 2,000 requests/sec**
2. Kubernetes HPA scales:

   * `order-service` from 3 → 10 pods
3. Prometheus automatically:

   * Discovers new pods
   * Starts scraping metrics
4. Grafana dashboards update **in real time**

   * Request rate increases
   * Latency stays stable
   * CPU usage spread across pods

No manual config needed.

---

# STEP 7: Detecting a Production Issue

### Problem:

Payment failures increase.

### Grafana shows:

* `payment-service` error rate jumps to 12%
* Latency spikes to 3 seconds
* JVM heap near 90%

### Prometheus alert fires:

```yaml
alert: HighErrorRate
expr: rate(http_server_requests_seconds_count{status="500"}[5m]) > 0.05
```

### Alertmanager sends:

* Slack message
* PagerDuty alert

---

# STEP 8: Root Cause Analysis

Using dashboards:

* Inventory service OK
* Order service OK
* Payment service:

  * GC pauses high
  * Memory leak suspected

Engineers:

* Roll back deployment
* Scale pods
* Fix code

---

# STEP 9: Post-Fix Verification

After redeploy:

* Error rate returns to <1%
* Latency normalizes
* CPU & memory stable

Grafana confirms system health **in real time**.
