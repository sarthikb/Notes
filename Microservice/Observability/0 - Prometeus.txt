Here’s a **detailed, structured, and practical overview of how Prometheus works** — covering its architecture, internal components, data flow, key concepts, and how it’s used in real-world monitoring.

---

## 🧠 What Is Prometheus?

**Prometheus** is an open-source systems monitoring and alerting toolkit originally developed at SoundCloud. It’s designed for reliability, simplicity, and powerful querying of time-series metrics.

It fundamentally works by **scraping metrics from targets**, storing them efficiently as **time-series data**, and providing **querying, alerting, and visualization** capabilities.

---

## 📊 Core Concepts in Prometheus

Before diving into the components, it helps to understand some core concepts:

| Concept         | Meaning                                                                     |
| --------------- | --------------------------------------------------------------------------- |
| **Metric**      | A numeric measurement recorded over time (e.g., HTTP requests, CPU usage).  |
| **Time Series** | A stream of metric values indexed by time and labels.                       |
| **Labels**      | Key-value pairs that add context to metrics (`method="POST"`, `job="api"`). |
| **Scraping**    | The act of Prometheus pulling metrics from a target.                        |
| **Exporter**    | A component that exposes metrics in a Prometheus-scrapable format.          |

---

## 🏛️ Prometheus Architecture – Internal Components

The Prometheus system is composed of interconnected components that handle collection, storage, querying, alerting, and discovery.

Here’s how they fit together:

---

### 1. 📥 Target Discovery

Prometheus needs to know **what to monitor**. Instead of static lists, it can discover targets dynamically:

✔ **Service Discovery**
Prometheus integrates with environments like Kubernetes, Consul, AWS, DNS, and more to automatically find services and endpoints to scrape.

✔ **Static Configuration**
Targets can also be defined manually via YAML config.

The list of discovered targets is fed into the **scraper**.

---

### 2. ⛏️ Scraper (HTTP Pull Model)

Prometheus uses an HTTP **pull-based** model:

* At configured intervals, it **scrapes** metrics from targets.
* Targets expose metrics via an HTTP endpoint (`/metrics`) in a specific format.

This is different from push systems — Prometheus **pulls** data instead of the client pushing it.

✔ Advantage: Prometheus controls timing, retries, and can monitor when targets disappear.

---

### 3. 📦 Exporters

Many systems don’t expose Prometheus-ready metrics natively, so **exporters** act as adaptors.

Examples include:

* **Node Exporter** – exposes OS metrics (CPU, memory, disk)
* **Blackbox Exporter** – probes endpoints (HTTP, DNS, TCP)
* **Database Exporters** – MySQL, PostgreSQL, Redis, etc.

Exporters run alongside or near the service and provide a `/metrics` endpoint Prometheus scrapes.

---

### 4. 📘 Time Series Database (TSDB)

Once Prometheus scrapes metrics:

* Each metric sample is stored in the **local Time Series Database**
* It stores data efficiently with compression, retention policies, and compaction

**Key features of TSDB:**

| Feature           | Purpose                                         |
| ----------------- | ----------------------------------------------- |
| **Chunks**        | Compressed blocks holding series data           |
| **Head Block**    | In-memory, write-optimized data                 |
| **Block Storage** | On-disk immutable blocks for efficient querying |

Prometheus uses a retention policy (e.g., 15 days) and periodically compacts older data.

---

### 5. 🔍 PromQL – The Query Language

Prometheus uses **PromQL**, a powerful time-series query language. It allows:

✔ Filtering by metric & labels
✔ Aggregations (`sum`, `avg`, `rate`)
✔ Time functions (`increase`, `irate`)
✔ Arithmetic & vector maths

Examples:

```promql
# CPU usage across all app pods
sum(rate(process_cpu_seconds_total[5m])) by (instance)

# 95th percentile latency
histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service))
```

PromQL powers dashboards and alerting.

---

### 6. 📈 Visualization (e.g., Grafana)

While Prometheus has a basic built-in graph view, most users connect it to **Grafana**:

* Grafana pulls data from Prometheus via PromQL
* Users build rich dashboards with charts, heatmaps, tables, alerts

Prometheus itself does not aim to be a full visualization UI — it focuses on data collection and querying.

---

### 7. 📣 Alertmanager

Prometheus sends **alert rules** to Alertmanager for notification and routing:

* Alertmanager groups alerts
* Suppresses duplicates
* Sends notifications via email, Slack, PagerDuty, SMS, etc.

Rules in Prometheus define when to trigger alerts:

```yaml
groups:
- name: node_alerts
  rules:
  - alert: HighCPULoad
    expr: node_load1 > 0.8
    for: 5m
    labels:
      severity: critical
    annotations:
      summary: "High CPU load"
```

Alertmanager handles deduplication, silencing, and routing.

---

## 🔄 Data Flow Summary

Here’s a timeline of how metrics flow:

1. **Service Discovery** finds new scrape targets
2. Prometheus **scrapes** `/metrics` endpoints on schedule
3. Data gets stored in the TSDB
4. **PromQL queries** retrieve and aggregate series for dashboards
5. **Alert rules** evaluate at intervals
6. Alerts are sent to **Alertmanager**
7. Alertmanager sends notifications via configured channels

| **Service Discovery**   | Scales with dynamic environments             |
| **Efficient TSDB**      | High performance on large metric volumes     |

## 🧩 Scaling & Remote Storage

While Prometheus is **single-node by design**, it can scale with:

✅ **Federation**
A hierarchy of Prometheus servers where a central server scrapes from others.

✅ **Remote Write / Remote Read**
Prometheus can send samples to external long-term storage (e.g., Cortex, Loki, Thanos, InfluxDB).

This keeps short-term monitoring local and fast while pushing older data to scalable systems.

## 🎯 Example Use Case

**Monitoring Kubernetes:**

* Kubernetes Service Discovery finds pods & services
* Pods expose metrics (via Prometheus client libs or exporters)
* Prometheus scrapes at intervals
* Grafana displays metrics like:

  * Pod CPU & memory
  * Deployment latency
  * Error rates
* Alerts fire when thresholds are crossed

## 🧠 When to Use Prometheus

Prometheus excels when you need:

✅ Real-time metrics
✅ Multi-dimensional label-based metrics
✅ Flexible querying & alerting
✅ Monitoring of dynamic cloud environments (Kubernetes)

---

## 🚀 Final Notes

Prometheus is **not a logs database or full APM tool** — it's focused on metrics. Often, it’s paired with:

🔹 **Grafana** (visualization)
🔹 **Loki** (logs)
🔹 **Tempo / Jaeger** (traces)

Together, they form a powerful Observability stack.
